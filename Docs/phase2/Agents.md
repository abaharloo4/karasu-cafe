# Agents.md — قوانین توسعه برای AI Agent

Repository: https://github.com/abaharloo4/karasu-cafe.git

## قبل از شروع هر توسعه

1. پوشه `/docs` بررسی و تمام فایل‌های زیر خوانده شوند (به همین ترتیب اولویت):
   `PRD.md` → `ARCHITECTURE.md` → `GUIDELINES.md` → `ROADMAP.md`
2. مشخص شود کدام فاز از `ROADMAP.md` در حال توسعه است. Phase 1 و Phase 2
   اکنون هر دو **قطعی و سفارش‌گرفته‌شده** هستند (باشگاه مشتریان هم اکنون
   رسماً بخشی از Phase 2 است). Phase 3 همچنان **مشروط و غیرقطعی** است —
   پیش از شروع کدنویسی روی آن (چند کافه، اپلیکیشن موبایل، SaaS)، تأیید صریح
   کارفرما لازم است.
2b. **پیش از شروع هر Task دیگر فاز ۲، «Task 0» (رفع نقص‌های امنیتی فاز ۱ —
   توکن واقعی، چک مالکیت روی endpointهای Loyalty، rate limiting، رجیستر
   `RoleMiddleware`) باید کامل شده باشد.** جزئیات در `phase2-cafe-management-prompt.md`
   و ARCHITECTURE.md بخش ۱۸.
3. هیچ تصمیمی که در `PRD.md` به‌عنوان "Out of Scope" علامت خورده، بدون تأیید
   صریح پیاده‌سازی نشود — حتی به‌صورت نیمه‌کاره یا skeleton. بازبینی کد فاز ۱
   نشان داد این قانون قبلاً نقض شده بود (OTP و Loyalty قبل از تأیید ساخته
   شده بودند، و هر دو هم ناقص/غیرفعال بودند)؛ این تکرار نشود.

## چک‌لیست امنیتی پیش از merge (از یافته‌های بازبینی فاز ۱)

هر Pull Request که یک route یا endpoint جدید اضافه می‌کند، باید این موارد را
رد کند:
- [ ] آیا این route هویت را از session/token احراز-هویت‌شده می‌گیرد، نه از
      یک id خام در body/query؟
- [ ] آیا روی این route (به‌خصوص OTP، لاگین، callback پرداخت) throttle اعمال شده؟
- [ ] آیا role/guard middleware مربوطه در `bootstrap/app.php` رجیستر و روی
      این route اعمال شده — نه فقط یک `authorize()` تنها در یک کنترلر؟
- [ ] آیا این قابلیت دقیقاً همان چیزی است که در `ROADMAP.md` برای فاز جاری
      تعریف شده، نه فراتر از آن؟

## ثبت Task ها

## قبل از هر تغییر کد

- `GUIDELINES.md` بررسی شود — به‌خصوص قانون «بدون Repository pattern» و
  «منطق کسب‌وکاری فقط در Service Layer».
- اگر تغییری با تصمیم معماری مستندشده در `ARCHITECTURE.md` تناقض دارد، اول
  خود آن فایل باید آپدیت شود، نه اینکه کد بی‌سروصدا از مستندات منحرف شود.

## بعد از هر تغییر

پس از هر تغییر کد که merge می‌شود:

1. شماره نسخه پروژه (در `composer.json` یا فایل version مشخص) افزایش یابد
   (Semantic Versioning: patch برای باگ‌فیکس، minor برای فیچر جدید، major
   برای breaking change)
2. `CHANGELOG.md` آپدیت شود (چه چیزی اضافه/تغییر/حذف شد)
3. اگر مشکلی حین توسعه پیش آمد و حل شد، رکورد آن در `DEBUG_LOG.md` طبق فرمت
   استاندارد ثبت شود
4. Commit با پیام واضح و مرتبط با task انجام شود (Conventional Commits:
   `feat:`, `fix:`, `docs:`, `refactor:`)
5. Push به repository بالا انجام شود

## Release

هر Release باید شامل:
- شماره نسخه (مطابق semver)
- Release Notes (خلاصه‌ای از `CHANGELOG.md` مربوط به آن نسخه)
- فایل ZIP خروجی، ساخته‌شده در root پروژه (بدون `vendor/`, `node_modules/`, `.env`)

**تذکر از بازبینی فاز ۱:** zip تحویلی قبلی، برخلاف همین قانون، شامل `.env`
واقعی (با رمز دیتابیس) و پوشه کامل `vendor/` (~۹۳ مگابایت) بود. پیش از هر
تحویل، به‌صورت صریح بررسی شود که `.env` و `vendor/` و `node_modules/` در
zip نهایی نیستند — این یک چک دستی الزامی است، نه فرض.

## قانون طلایی

هیچ تغییر کدی بدون به‌روزرسانی مستندات مرتبط (`PRD.md`, `ARCHITECTURE.md`,
`ROADMAP.md`, `CHANGELOG.md`) انجام نمی‌شود — مستندات باید همیشه بازتاب‌دهنده
وضعیت واقعی کد باشند، نه وضعیتی که در ابتدای پروژه تصور می‌شد.
